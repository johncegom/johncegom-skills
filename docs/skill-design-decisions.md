# Skill design decisions

A running log of judgment calls made while authoring skills, mods and repo tooling in this repo — what was decided, why, and what was rejected.

## 2026-09-16 — `learn-technology-by-building`: sharpen the existing learner-profile mechanism instead of adding a second "Dream" section

**Decided.** Cross-session learner-pattern capture stays inside the structures that already exist: a "Recurring flags" paragraph appended to the trap-check section (log to `references/learning-profile.md` only on a *second* occurrence — same trap twice, a logged decision failing recall twice, the same copy→disturb→transfer step rebuilt twice, or recall failures clustering by concept type), one line in "Maintain continuity" separating the ledger (project state, every meaningful progress) from `learning-profile.md` (learner patterns, second flagged occurrence), and a tightened "Mentor interpretation" section in `references/learning-profile.template.md` that updates only once something repeats. No new `## Dream` section, and no edit to the shared `execute-advise-grade-dream.md` reference doc.

**Why.** The proposal's genuinely new content was the rigor, not the mechanism: a hard trigger condition, a "learner patterns, not project state" boundary, and a second-occurrence gate. All three attach cleanly to `learning-profile.md` and its template, which are already read every session and already have the right homes for this data ("Evidence from prior projects", "Mentor interpretation"). Labeling a new mechanism "Dream" would have forced a correction to the shared reference doc, whose worked example (lines 85-88) names this skill's continuity ledger as its Dream role — leaving the skill with two differently-triggered things called Dream for zero learner-facing gain. A per-flagged-trap Opus spawn also fights the skill's own budget discipline: never displace building, no standalone ceremony.

**Rejected.** Adding a new top-level `## Dream: capture learner patterns` section after the trap check, with its own Opus spawn on every flagged trap. Rejected for the duplicate-Dream conflict above and for the per-trap cost. (The proposal also pointed at `references/execute-advise-grade-dream.md` inside this skill, a path that doesn't exist — that doc lives in `plugins/minh-toolkit/skills/bootstrap-eagd-pattern/references/` and in this repo's `docs/`.)

**Generalizes to.** When a proposal's real value is added rigor rather than a new capability, attach the rigor to the structure that already owns the data. Reserve a role label like "Dream" for one mechanism per skill — a second one contradicts the shared reference doc's characterization and buys nothing.

## 2026-09-18 — EAGD: Advise fires on observable conditions, and the general rule lives in the reference doc while the repo-specific instance lives in `CLAUDE.md`

**Decided.** Advise's trigger stops keying on Execute's felt doubt and keys on conditions an outside reader could check — kind of decision, stage, or a fixed budget (in this repo: one call on scope for every new `SKILL.md` or changed `description` line, always). Questions are routed by type rather than escalated in sequence: verifiable → research, preference → the user or a stated conventional default, judgment → Advise; stated explicitly as a filter that adds no approval checkpoint. Context regime is the middle one: question + Execute's prior leaning with the case for and against + the artifacts verbatim, plus a request that the advisor name context it lacked. Execute writes its leaning before calling and appends one line per call to `docs/eagd-log.md`, which is what the re-calibration thresholds now read. The four general rules went into `docs/execute-advise-grade-dream.md` (and its `plugins/minh-toolkit/references/` twin) under a new "Advise's trigger and context" section; the repo-specific triggers went only into `CLAUDE.md`.

**Why.** A felt-doubt trigger is silent exactly where it costs most — the confident wrong call — and the old cost clause ("redoing already-merged work") collapsed to always-or-never depending on how strictly it was read in a PR-gated repo. A fixed budget is immune to overconfidence and caps cost by construction. The split of general rule from concrete instance follows from what each doc is: the reference doc describes the pattern for any kind of work, so skill-specific triggers would be false there, while `CLAUDE.md` is read every session, which also decided the length question — the reference section was cut ~610 → ~330 words and the `CLAUDE.md` paragraph 27 → 18 lines with nothing dropped, because per-session reading cost is the scarcer budget. Logging exists because the previous re-calibration paragraph named conditions ("fires on nearly every edit", "hasn't fired in many sessions") that nothing in the repo could detect; a prior-leaning line plus an outcome line yields a decision-change rate, the only signal separating a steering advisor from a rubber stamp.

**Rejected.** Keeping "genuinely ambiguous" and merely tightening the cost clause. Putting the repo-specific triggers into the reference doc as worked examples. The first draft's "Advise is the third resort" framing (look it up → ask the user → Advise), which reads as three sequential gates and would put a user question before every Advise call. Full conversation history as the advisor's context — the user floated it, but it makes the advisor inherit Execute's reasoning (the very trap Grade is insulated from), costs the most in the pattern, and is unavailable anyway in a harness where a forked sub-agent ignores the model override. Minimal curated context, for framing bias.

**Generalizes to.** State a spawn trigger as something checkable from outside the agent's head; "when you're unsure" is not a trigger. Give any standing mechanism a cheap log of its own firings, or its stated re-calibration conditions are unobservable. When guidance has both a general form and a repo-specific instance, put the general form where the pattern is defined and the instance where it is executed — and optimize length against how often each document is actually read.

## 2026-09-18 — `bootstrap-eagd-pattern`: bind each role to a concrete model keyed by the sub-agent tool the session holds, and gate every binding on an install-time probe

**Decided.** The standing directive names a concrete model id per role, keyed not by vendor but by the sub-agent **tool** the session actually holds — something a session can read off its own tool list, where the vendor can only be guessed. A row is written into the anchor doc only after an install-time probe: spawn the model through that tool, have it report its own id, compare against what was requested. Rows live between fixed start/end marker comments in a machine-stable `(role, tool)` grammar with status `ok` / `unverified` / `stale`, so a later run can rewrite one row without pattern-matching prose. With no verified row for the held tool, Advise and Dream **skip**; Grade may fall back to a fresh same-model call and logs that it did. The advisor's first reply line reports `model: <id>`, and the log carries tool / requested / reported. Re-running the skill in a harness that already has rows is a re-calibration, not a fresh install: probe only rows the run touches (or on an explicit "verify"), leave cannot-probe rows untouched, report rows for tools this session does not hold as not re-verified. Execute added one step neither advisor proposed — probe once with a model *different* from the session's own before probing the requested one, since an Opus session probing "opus" passes even when overrides are silently ignored. The log became real markdown: three tables (Advise calls, Binding changes, Grade fallbacks) with a countable Status column, and an instruction to follow the target file's own format when the user points the log at an existing jsonl/csv/decision file.

**Why.** The decisive asymmetry is observability: the held tool is in the session's own context, the vendor is not, so keying on the tool removes a guess from the hot path. Probe-gating exists because nothing else distinguishes "this harness honours a per-call model override" from "this harness quietly ignores it" — and this repo is already a live example, since `CLAUDE.md` names `claude-opus-5` while the Agent tool's `model` field takes aliases. The skip-don't-fall-back rule for Advise and Dream is the sharpest call: a same-model "consultation" would fill `docs/eagd-log.md` with rows that look healthy, inflating firing rate while pushing decision-change rate toward zero — corrupting exactly the two signals the re-calibration trigger reads. Grade is different; it is insulated by fresh context rather than by a different model, so a same-model rerun still does its job as long as the log says so. Marker-delimited rows follow from a re-run needing to update in place, which is unimplementable against free-form prose.

**Rejected.** Capability tiers ("a strong model") as the directive — it defers model choice to the Execute session mid-task and Step 3 already forbids that phrasing. Vendor self-identification by prose heuristic, and a maintained vendor/model matrix in `references/`, both guesses that rot. Per-vendor binding lines in each harness's own file (killed once the user established all vendors read the same `AGENTS.md`). Re-probe-every-row-by-default, as over-engineered: a rename is caught at runtime by the reported-vs-requested check, a better detector than a periodic self-report. Date-based staleness warnings, for the same reason. Idea C — a repo script shelling out to one pinned vendor CLI so every harness gets the same advisor — kept only as an opt-in for Advise, since it needs that CLI installed and authenticated. Cross-vendor Advise is a side effect of the design, not its goal.

**Generalizes to.** Key a standing directive to something the executing session can observe about itself, not to something it must infer about its environment. When a mechanism's health is measured by a log, forbid the fallback that writes a healthy-looking row for a call that did nothing. Verify a capability at install time rather than asserting it in prose — and design the verification so it cannot pass trivially. Notable for the re-calibration trigger: Execute's leaning was overturned by Advise in two of the three rounds (the binding table, then capability tiers), and Grade passed all four rubric items, though item 3 (contradiction with other installed skills) was a weak pass — the grader named two skills as consistent without quoting them.

## 2026-09-24 — `bootstrap-eagd-pattern`: add an out-of-tree storage scope for repos that can't hold agent files, and drop the local-untracked middle option

**Decided.** The existing skill gains one short section, "Storage scope: committed or out-of-tree", that defines `<state-dir>` and the loader once so no later step has to branch on mode. Fresh installs ask once, with committed as the stated default; re-runs don't ask. Out-of-tree keeps the directive, binding rows, rationale doc, log and Dream file under `~/.claude/eagd/<repo>/`, with a conditional user-level pointer keyed by the remote slug. Re-run detection now also looks out-of-tree, since otherwise every re-run would look like a fresh install. The section names its two limits (teammates don't get the mechanism; if org policy also covers `~/.claude`, this mode doesn't satisfy it) and says explicitly not to offer local-untracked. Out-of-tree gets a manual canary the user runs, not a spawned test, and Step 6 gains a sentence: check the directive actually loads before narrowing a trigger. The description and README row say "or kept outside the repo when it can't hold agent files"; plugin 0.12.0 → 0.13.0. Along the way, Step 4's ambiguous `references/` path now says "at the plugin root, not inside this skill's folder". The reference doc was never missing, as an earlier claim in this run had said.

**Why.** The probe, binding rows, log, re-run and skip/fallback rules are the hard part and don't change with storage scope. A sibling skill would duplicate them and drift, a `references/` file can't change the install flow, and `CLAUDE.md` is this repo's instance rather than the product. Local-untracked (files hidden via `.git/info/exclude`) looked like a cheap middle option, but the directive has to load from a file read at session start. That file is usually a tracked `CLAUDE.md`, so this mode needs an untracked loader anyway, which is the whole difficulty of out-of-tree without its durability: it vanishes on re-clone, worktrees share the exclude but not the files, and files in `docs/` pass for normal docs. The canary is manual because nobody has confirmed that a sub-agent loads user-level files the way a top-level session does. A "role never fires" reading in Step 6 could then be a placement fault misread as a trigger problem. Execute's leaning changed on two points, dropping local-untracked and making the canary manual rather than automated.

**Rejected.** Three modes with local-untracked in the middle, and `.gitignore` in any mode (it is itself a committed change). An automated sub-agent canary. A new sibling skill. Wording that depends on `CLAUDE.local.md` or path-scoped rules. Moving committed-mode bindings out of the anchor doc in this PR. Bindings are per-user probe results and arguably don't belong in a commit, but moving them changes behaviour for existing users, so that's a follow-up.

**Generalizes to.** When a constraint only changes *where* a mechanism's state lives, resolve the location once in one place and keep the steps location-blind. Before offering a "cheap middle" option, check it doesn't carry the expensive option's hardest dependency, here an untracked loader. Don't automate a check whose premise is unverified; make it manual and tell the user what it proves. For the re-calibration trigger, this run's Advise reply reported `claude-opus-5-5` against a row reading `claude-opus-5`. That was the first time the stale-binding rule fired for real: the row went `stale` and the change was logged, which is the runtime rename detection the 2026-09-18 entry relied on. Grade (haiku, id matched) passed all four items, with item 3 again a weak pass because it quoted nothing.

## 2026-09-25 — `bootstrap-eagd-pattern`: make the description harness-neutral, and fix the two body lines that would make a portability claim false

**Decided.** The description becomes a folded `>` scalar, per repo convention (it had been unquoted). Its do-not-trigger list names `CLAUDE.md`, `AGENTS.md`, and Copilot or Cursor rules instead of `CLAUDE.md` alone. Invocation is "by name", and the `/bootstrap-eagd-pattern` slash command appears only "where the harness supports slash commands". It now says the skill works on any harness with a sub-agent tool, optimised for Claude Code. Two body lines changed in the same PR so that claim holds: the directive the skill writes into the target repo's anchor doc no longer names `AskUserQuestion` alone but adds "or your harness's ask-the-user tool, else ask in plain text", and the out-of-tree default `~/.claude/eagd/<repo-key>/` is marked as Claude Code's default, with any stable per-user dir fine elsewhere.

**Why.** A critical read found the description already mostly neutral ("harness's sub-agent tool", "anchor doc"). The real Claude-isms were the bare `CLAUDE.md` and treating the slash command as the way to invoke it. The body was worse where it mattered: `AskUserQuestion` sits inside generated text that a Copilot, Codex or Cursor session will read and cannot act on. Execute leaned toward a description-only edit, with the body lines reported as follow-up and no portability claim. Advise (opus, reported `claude-opus-5-5`, matching the row) agreed with the description edits but said "works on any harness" is not a trigger condition and doesn't help routing, and is only honest if the generated directive stops naming a Claude-only tool. So either drop the claim or fix the two lines in the same change. It recommended fixing them, and that was taken.

**Rejected.** A description-only edit, whether it kept the portability claim over a Claude-only body (oversells) or dropped it for a hedge (unhelpful). A general portability rewrite of the body, as out of scope: only the two lines that would make the claim false were touched.

**Generalizes to.** A capability claim in a description is only as true as the text the skill emits. If the claim goes in, fix the emitted text in the same change, or leave the claim out. When checking portability, read what the skill generates for other sessions, not just its own prose, since that is what other harnesses actually load. For the re-calibration trigger, Advise changed Execute's leaning here (description-only became description plus two body lines), and Grade (fresh haiku) passed all four rubric items.

## 2026-09-25 — `codebase-onboarding`: a new standalone skill with a narrow onboarding trigger and a self-contained verification pass

**Decided.** Fast onboarding into an unfamiliar codebase ships as a new auto-triggering skill, `codebase-onboarding`. The agent reverse-extracts architecture and business-logic specs, checks that understanding with a separate verification pass, and saves notes plus a first-PR checklist to a folder outside the repo. The trigger requires the onboarding framing ("just joined", "picked back up", "need the core fast") and excludes a quick question about one file, function or flow, writing onboarding docs for others, and designing new architecture. The verifier is defined entirely inside the skill and named "verification pass", not "Grade". It has no links to this repo's EAGD bindings, `CLAUDE.md` or `docs/`. The skill also proposes a default notes folder outside the repo and refuses paths inside it. A returning run updates the notes rather than regenerating them, and the first-PR checklist is grounded in evidence found in the repo. There is a scoping step for large repos, the target repo is read-only, and project code is not run without asking. An explain-back comprehension step is a single optional offer at the end. Plugin 0.13.2 → 0.14.0.

**Why.** Execute and Advise (opus, reported `claude-opus-5-5`, matching the row) agreed on standalone. Advise moved the main risk from overlap with `learn-technology-by-building` or `engineering:documentation` to over-triggering in a coding harness, where "help me understand this" is constant, so the fix is a narrow trigger rather than a merge. The README tagline ("coaches you instead of doing the work") doesn't block it, since several toolkit skills already do the work. Whether to force an explain-back is a user preference, so it became an offer and the obvious default was taken without asking. The verifier has to be self-contained because a per-skill install ships none of this repo's EAGD files, and reusing the name "Grade" would blur it with the repo's own role.

**Rejected.** Extending `learn-technology-by-building` or `goal-to-code-unblock`, a `references/` file, or a `CLAUDE.md` rule. A broad "understand this codebase" trigger. A verifier that borrows the repo's Grade binding. A mandatory explain-back step.

**Generalizes to.** When a new skill sits in a harness where its trigger phrase is everyday talk, the risk to design against is over-triggering, not sibling overlap. Require the framing and list what it excludes. A skill that ships to other installs must define its own sub-mechanisms inline and name them so they aren't confused with the authoring repo's roles. For the re-calibration trigger, Advise changed Execute's leaning on three points (trigger scope, optional explain-back, self-contained verifier). Grade (fresh haiku) passed all four items, with item 4 N/A. Item 3 was again a weak pass: it named four sibling skills as consistent without quoting any.

## 2026-09-28 — `codebase-onboarding`: give the notes a destination and a throughline, and end on a next action instead of a quiz

**Decided.** The skill now uses the Goal it already captured. Step 1 gains a "carry the Goal forward" sentence. The architecture spec requires one primary flow traced end to end. The business-logic spec's line that said to describe what the code does "instead of guessing a purpose" is rewritten, not appended to. It now requires why-claims only for load-bearing or Goal-relevant rules, sourced from commits, ADRs, tests or contrast in the code, and marked (inferred) where they are. The verification pass checks why-claims like any other claim. The first-PR checklist prefers a Goal-relevant first change when one exists. Step 5 is reordered: next action first, then one goal-tied prediction (at most one, "not a quiz round"), then where the notes are and the open questions. A user who says up front that they only want passive notes skips the prediction. The frontmatter description is unchanged, so routing is the same.

**Why.** Real feedback after use: the docs were fine, but afterwards the user felt blank, "so that is it, and, now what?". Offered a menu of causes, they picked "the docs themselves are the problem" and explicitly not "I should engage more". Execute's leaning was to add a "why" dimension, end on an action, and flip the optional comprehension check to run-by-default. Advise (opus, reported `claude-opus-5-5`, matching the row) read the shipped file and found a sharper root cause. Step 1 captured the Goal and nothing downstream used it, so the specs described the whole repo with no destination. No single flow was traced, so there was no narrative. And the existing business-logic line forbade "why", so appending a why-requirement would have left the skill contradicting itself. Advise scoped why-claims to load-bearing or Goal-relevant rules to protect the one-sitting length rule. It also rejected the default-on quiz, because the user had ruled out engagement as the cause and a mandatory check would treat the wrong one. It folded a single prediction into the next-action step instead. Advise also noted that this is the one toolkit skill that does the work outright, against the README's "coaches you instead of doing the work for you". The change moves it slightly toward the tagline without making it a coaching loop.

**Rejected.** A comprehension check that runs by default with an opt-out. Appending a why-requirement next to the line that forbade it. Why-claims on every component. Leaving step 5 ending on a document dump plus an easy-to-decline offer. Touching the description.

**Generalizes to.** When a user names the cause of a failure, fix that cause; a mechanism aimed at a cause they rejected is the wrong fix even if it would help someone. Before adding a requirement to a skill, read for an existing line that forbids it and rewrite that line in the same change. An input a skill collects but never uses downstream is a likely root cause of output that feels aimless. For the re-calibration trigger, Advise changed Execute's leaning on the central point (no default-on quiz; a Goal throughline and a flow trace instead). Grade (fresh haiku, five-item rubric including the new harness-portability item) passed all five. Item 3 was a strong pass this time: it quoted the "not a comprehension-check ceremony" and "do not turn this into a quiz round" lines as evidence of no drift into `goal-to-code-unblock` or `learn-technology-by-building` coaching loops. SKILL.md went from 6113 to 7910 bytes, under the 20000-byte CI budget.

## 2026-09-28 — `codebase-onboarding`: drop the reference-study situation, rebuild opt-in diagrams and concepts off #66 with a deviation test and generate-then-prune

**Decided.** Two same-day PRs were closed unmerged, with comments explaining why, rather than merged and later reverted, since neither had shipped: #67, which added a fourth "reference study" situation for studying a repo to build a different app, and #68, which added an opt-in architecture diagram and a `general-concepts.md` file on top of #67. The user's call, verbatim: "Remove the reference study (#67 I think). Strengthen for the diagram and general concepts (or something that abstract and can reused as knowledge, then apply into other project)." A fresh branch, `feat/codebase-onboarding-concepts-v2`, was cut from #66 (the last validated, shipped-quality state), not from the closed branches, so no reference-study residue carried forward. The concepts mechanism now works like this. Draft 8-10 candidates, then run each through three gates. The **deviation test** asks the candidate to name the default a competent engineer would reach for, what this repo did instead, and the concrete cost or failure that justified the difference. The **grounding gate** requires traceable repo evidence (a commit or revert, an ADR, a test that encodes a past failure, a documented contrast), and "a pattern I noticed" doesn't count. The **swap gate** asks whether the concept still holds with a different language, framework or domain. Survivors are kept with no floor and a cap of 5. A "Considered and cut" section names each rejected candidate and why. The verification pass's fresh sub-agent also judges whether each kept concept could have been written blind from the README alone. Diagrams and concepts both stay opt-in, and the run still asks the user rather than deciding for itself. The description was rewritten to mention the capability and trimmed back under the 1024-character limit (~969 final) after the CI frontmatter check caught it over again. README got one use-case line and one skill-table row. Version 0.14.2 → 0.15.0, counted from #66 and not from the abandoned 0.15.0/0.15.1 bumps.

**Why.** Execute ran an unprompted critical review of all three same-day PRs, asking "how does this fail" rather than "does this sound reasonable". It found two distinct problems. #67 had purpose drift. The case for keeping it in the same skill was reuse of the implementation machinery (steps 2-3), not evidence that the task was the same. Because the Situation is inferred rather than asked, ordinary onboarding phrasing like "help me understand this codebase's architecture" could land someone on their first day at a new job in the wrong output shape. #68's concepts file was speculative. Unlike the #66 engagement fix, which was validated against a live repo, #67 and #68 were designed and shipped from conversation alone. The swap test on its own pushes toward safe, generic phrasing almost by construction, so the file could fill with platitudes and nothing would catch it. Advise (opus, reported `claude-opus-5-5`, matching the row) was asked how to prevent that. It replaced Execute's fuzzy "surprise test" (would a competent engineer already assume this?) with the mechanical deviation test. It widened the grounding evidence while ruling out mere noticing, and restructured the process as generate-then-prune, because a short kept list next to an honest cut list reads as a finished judgment rather than a thin one. It also added the blind-writability check to the verification pass as a cheap stand-in for a real blind baseline. Before shipping, Execute ran the gates by hand on real material: the verified architecture and business-logic specs from an earlier real test run against `go-youtube-mcp-cli`. The original notes files were gone from disk, so the content came from this conversation's history, and that was flagged rather than presented as a fresh read. Of 9 candidates, 5 survived. Two were cut by the deviation gate as ordinary default choices, one as redundant with a kept entry that covered the same insight from another angle, and one as a fairly standard, guessable tradeoff, to respect the cap. The blind check on the 5 survivors was reported honestly: 4 were clearly not guessable from the README, and 1 was only partly non-obvious (the framing was guessable, one implementation detail was not). Grade (fresh haiku, given SKILL.md and `references/diagrams-and-concepts.md` together, told to hunt for reference-study residue) passed all 5 rubric items and all 6 specific checks. It confirmed that "reference study", "reuse dossier" and "adopt/adapt/skip" appear nowhere in either file.

**Rejected.** Keeping the reference-study situation in this skill, and merging #67/#68 only to revert them later. Building v2 on top of the closed branches. The "surprise test" as the concepts filter. Writing concepts straight to a kept list without a visible cut list. Two Advise proposals were declined outright. The first was a cumulative cross-repo concepts library, which would use recurrence across repos as evidence that a concept is real. The second was making concepts default-on while only diagrams stayed opt-in. Both reversed decisions the user had made explicitly earlier that day, and Advise hadn't been told about them: probe on every run rather than self-decide, and no persistent cross-repo file, because most real use is onboarding into confidential work repos where cross-repo accumulation is hard to do safely. Execute overrode Advise to keep a prior explicit user decision that Advise had no context on. It was not a finding that Advise was wrong on the merits in isolation.

**Generalizes to.** Reusing implementation machinery is not evidence that two tasks belong in one skill. When the mode is inferred rather than asked, a second task behind a shared trigger is a misclassification risk that lands on the core use case. A filter meant to stop platitudes has to be mechanical (name the default, the deviation, and its cost) and paired with a visible cut list, not a judgment call like "would this surprise someone". Test a new generative mechanism on real material before shipping, and report a partial pass as partial. When shipped work turns out to be wrong but unmerged, close it and rebuild from the last validated state instead of layering fixes on top. When passing context to Advise, include the user's prior explicit decisions. If Advise's answer reverses one it wasn't shown, keep the user's decision and log the override so it isn't counted as Advise being wrong. For the re-calibration trigger, Advise changed Execute's leaning on the core mechanism (surprise test → deviation test, write-directly → generate-then-prune). Two of its proposals were declined for missing user context, which is a context-packaging gap, not an advisor-quality signal. Grade (fresh haiku) passed everything.

## 2026-09-28 — `sound-human`: one shared short-draft carve-out for the count-based checklist items, and a harness-neutral fallback for the Grade-model line

**Decided.** Two body edits, found while writing the skill's first fuzz case under `tests/sound-human/fuzz/`. First, a single "Short drafts (one paragraph, or only a sentence or two)" clause sits directly under the Quality Checklist. It says that count or percentage items which can't structurally apply to a short draft ("at least 30% of paragraphs don't end with a neat conclusion", "at least one sentence starts with And or But", "no mirror structures") are satisfied by omission, not by adding structure to meet them. Second, the line telling the skill's own Grade pass which model to use changed from "Run this Grade pass on Sonnet, not the usual Haiku default" to "on Sonnet, or your harness's most capable available model, not the usual lighter default". The later "Haiku" mentions in that paragraph became "a lighter/faster model" and "the stronger model". The frontmatter description is unchanged.

**Why.** The checklist said to verify every item, yet the same skill's Output Format handles single-paragraph drafts under 300 words and its LinkedIn rules want a one-line hook. An agent held to both would pad or split a short draft to tick boxes, which breaks the skill's own "What to Protect" rule ("Don't over-correct into a different kind of artificiality"). The failure is the same for every count-based item, so one shared clause covers it. For the model line, Grade (fresh haiku) failed rubric item 5 on that line alone, since it names model aliases as the model to request with no fallback. Items 1-4 passed. Grade judged it a single-line targeted fix, not a redraft. The skill's mechanism, a three-pass rewrite plus a grading pass on a stronger model, needs no Claude-only tool. Only the wording was the problem, so Sonnet stays as the Claude-first recommendation and other harnesses get a fallback beside it. No Advise call: the change was body-only with an obvious home, so no trigger condition was met.

**Rejected.** Adding an "if applicable" qualifier to each of the 17 checklist items, which would make the list longer and repetitive for one shared failure. Declaring the skill `Claude Code only` to clear item 5, which is too much of an opt-out for a one-line wording problem when nothing in the mechanism depends on Claude.

**Generalizes to.** A "verify every item" checklist needs an explicit rule for items that can't apply, or agents will manufacture the structure to satisfy them. Check count-based rules against the smallest input the skill says it handles. When several items fail the same way, fix them with one shared clause rather than a qualifier on each. The AbovePrompt hook wraps `await next(e)` instead of returning only its own tree, so mods beneath it still draw. Built as its own plugin (`plugins/fuse`): pure logic in `core.ts`, hooks in `register.tsx`, 22 tests on a fake clock; `claude plugin validate` and the safety scan pass. The owner checked a real hold live: left open about 5 minutes, then Extend still worked (Windows).

**Why.** Execute read `$.process.run` as a one-shot child process and called it the wrong tool for waiting. Running the code showed the rule that decides it: a hook has a 10 s budget of its own time, `$.clock.sleep` spends it, and time awaiting another `$` call does not. A hold that waits minutes for a human can only wait through `$.process.run`. Second, inside one running hook dispatch, repeated `$.state` reads kept returning the first value seen (observed, not documented), so the polling loop never saw the press; it looked like a dropped hook and took several toast-tracing rounds to find. It showed up live too: two parallel tool calls were held, and the one that waited behind the other re-checked the turn with a plain read, missed the owner's Stop and opened a second hold, so Stop needed two presses (Esc, `2` and a click all did). Reading the turn through `update`, which writes and returns the live value, fixed it; the owner confirmed one press now stops both. Third, the owner's live test showed fuse replacing usage-band, because a hook that ignores `next(e)` replaces every mod beneath it.

**Rejected.** `$.clock.sleep` for the hold (spends the hook's own budget). Polling `$.state` for the answer (stale within a dispatch). Returning only fuse's own tree from AbovePrompt. Left as is: usage-band and skill-badge still replace each other, a pre-existing defect and a follow-up.

**Generalizes to.** Before overruling a concrete detail in an owner's spec, read the API docs for that call in full and run it; a type signature alone is not grounds. If a correction turns out wrong, say so to the owner plainly. For mods: wait for a human through an in-flight `$` call, not the hook's own clock (`HookBudget` counts a `$.clock` wait); prefer module memory over `$.state` for a press handler's answer (stale reads seen in the test harness and live); compose with `next(e)` unless you mean to replace what is beneath. Test a hold with parallel tool calls: one answer must cover all of them. No Advise or Grade ran during the fuse build (a mod has no SKILL.md).
