# Reusable templates

Use these as compact frames. Adapt labels to the technology and omit empty sections that add no value.

## Roadmap frame

```markdown
# <Technology> through <Cumulative Project>

Outcome: <independent capability>
Project: <small end-to-end system that can grow>
Practice mix: ~80% cumulative project / ~20% isolated experiments
Pace: <weekly capacity; flexible targets>

## Phase <n> — <capability>

Weekly outcome: <working behavior>
Evidence of completion: <command, output, tests, or explanation>
Concepts introduced: <only concepts required by this phase>
```

## Checkpoint frame

```markdown
Checkpoint <n> — <small working outcome>

Why now: <problem this solves>
Change: <files and minimal implementation>
Run: <exact command>
Expected: <observable output or test result>
New idea: <plain explanation + mapped metaphor>
Visual model: <diagram type and what relationship it makes visible>
Break it: <one controlled variation>
Transfer: <one small independent modification or explanation>
Done when: <evidence>
```

## Resource prescription

```markdown
Resource: <title and link>
Study only: <chapter, timestamp, or section>
Extract: <two to four precise ideas>
Skip for now: <unneeded sections>
Apply immediately: <project task>
```

## Why-this-choice explanation

```markdown
Problem: <current pressure or failure>
Choice: <selected approach>
Why it fits now: <benefit at the learner's current stage>
Why not the main alternatives yet: <concrete tradeoffs>
How it works: <mechanism>
Metaphor: <analogy mapped to mechanism and boundary>
Revisit when: <signal that another choice has become justified>
```

## System-design visual checkpoint

```markdown
Question: <structural or runtime relationship to understand>
View: <context, container/component, sequence, state, data flow, or deployment>
Scope: <what the diagram deliberately includes and excludes>

Map:
<focused Mermaid diagram>

Trace:
- Happy path: <follow the arrows in order>
- Failure/concurrency path: <what changes and where>

Redraw:
- <reproduce from memory, fill missing nodes/edges, or derive from code>

Challenge:
- New constraint: <traffic, consistency, failure, security, or ownership change>
- Predicted diagram change: <nodes, edges, boundaries, or annotations>

Explain:
- Why one important component exists:
- Tradeoff accepted:
- Signal that would justify redesign:

Done when: <learner redraws or modifies the view and explains the changed flow>
```
